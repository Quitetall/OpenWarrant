# Battery plants that fail only under parallel load

During the evidence wave (three ops.conformance.plants@1.1.0 batteries at once on a loaded machine, 2026-09-25/26), plants failed that pass when run alone. Tracked elsewhere: t-26ca (webui 431 → 000), t-470e (59-webui-lan sleep 1), t-0e4f (plant 64 fixed /tmp path), t-9d3e (ready/claim disagree — a real bug). Not yet tracked, here: (a) 54-intake 'a drafted Warrant awaits a human' read empty JSON ('Expecting value: line 1 column 1') and 'a pre-approved body changes nothing' followed — some command produced no output under load (OW-WAR-0124's run); (b) 67-pins-next 'next answers this corpus in time' measured 7723 ms against its 6000 ms bound (OW-WAR-0137's run). A wall-clock bound in a battery that runs in parallel must be relative (e.g. to a baseline command timed in the same run) or generous enough for the load the gate is run under.

## Notes

- **2026-09-26 03:03 UTC, claude:** Likely common cause (OW-WAR-0141's run: 00-corpus 'the page reaches for nothing' → exit 127, i.e. ./target/debug/war not found): plant-isolated.sh points every clone's target/ and CARGO_TARGET_DIR at the SAME build directory, and 89-schemas runs `cargo run` inside each clone. Each clone sits at a different path, so cargo sees changed sources and relinks target/debug/war while other batteries are executing it — a missing binary (127) or a half-written one (empty output, e.g. 54-intake's JSON). Parallel batteries sharing one target dir are unsound. Fix options: 89-schemas uses the built binary instead of cargo run; or plant-isolated gives each run its own target dir (a full build per run); or the gate refuses to run concurrently with itself (a lock). Receipts that PASSED in parallel are still sound (same commit, identical build); failures must be rerun serially.
