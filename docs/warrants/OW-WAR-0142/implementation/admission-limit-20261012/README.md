# Standing authorization admission limit

Two overlapping applications to a real signed fixture class with `max_warrants = 1` both returned success and wrote authorizations. They have distinct aliases and contract digests, the same accepted class, and the same timestamp. The class view reports two uses against a limit of one. This is an observed control failure, not an inferred source concern. Only disposable fixture keys and synthetic actors were used.

The previous admission count used the historical `(timestamp, alias)` ordering. It could ignore a claim with a later alias or timestamp, and it silently skipped an unparseable authorization. It also checked capacity and wrote different aliases without a shared transaction guard. The fix separates current admission counting from historical validation, propagates unreadable count inputs as UNKNOWN, and holds an advisory directory lock across the coverage/ownership checks, authorization write and journal operation. A busy or unsupported guard returns UNKNOWN without writing. Historical timestamp ordering is retained; class identity comparison now includes accepted alternate revision spellings. No schema, permission, signature or past record is rewritten.

Before the fix, two new unit tests fail (two existing tests pass) and two CLI controls fail (46 pass). The original overlapping-request probe now records exactly one authorization; its concurrent peer is refused with exit 2. A later retry observes actual exhaustion. An independently held admission guard writes nothing. An unreadable prior claim returns `standing.capacity-unknown`, exit 2, with no authorization and an unchanged target tree. The initial selected standing controls pass 49/0 and standing units pass 4/0. CLI Clippy on all targets and formatting pass. The first unit harness compile used an unavailable UUID dependency and ran no tests; the corrected harness uses the standard library. A final control attempt correctly refused authored-record edits in its checkout; the full 49 controls then ran in an owned disposable corpus.

This is cooperating CLI admission protection for one corpus, not sandboxing, tamper-proof file storage, or distributed quota enforcement. Linux runtime is observed; other platforms and the full final-candidate gate remain separate. The current repository's read-only class inventory is empty, so this does not establish an operator's first class or exercise their custody. The binary identifies its dirty implementation build basis rather than a clean final evidence commit.
